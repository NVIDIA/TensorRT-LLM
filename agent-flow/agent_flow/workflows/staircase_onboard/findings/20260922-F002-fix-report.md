## The new schema surface

`members` is a list of concrete parallel segments, or a mapping from assembly
unit to one layered over `default`. It is legal only with `parallel: unified`.

```yaml
parallel: unified

# Applies to every unit.
members: [tp4, tep4, dep4]

# Or, per unit — the knob for buying a cheaper answer honestly:
# members:
#   default: [tp4, tep4, dep4]
#   multimodal: [tep4]
```

Rules, each enforced with a message that names the fix:

- **only under `parallel: unified`** — a concrete segment already names the
  one configuration, and two declarations of the same thing can disagree.
- **`unified` is not a legal member** — it is the family, not a member of it;
  accepting it reintroduces the TP-only gate under a new name.
- **one world size across all members** — one allocation serves them all; a
  mismatch is reported naming both members and both numbers.
- **default when omitted**: `[tp<W>, tep<W>, dep<W>]` — the baseline pair plus
  the degenerate path, at the unified world size.

Resolution lives in exactly one place, `task_schema.members_for(data, unit,
world_size)`. For a concrete segment it returns `[that segment]`, so the
orchestrator has one code path and the single-configuration run is the
degenerate case rather than a branch.

Every verdict now names its member:

```
[PASS] boot@tep4: engine cold-started and produced non-empty generation (61s)
[PASS] accuracy[gsm8k]@dep4: measured 95.9000 vs reference 95.5300 - tol 5.00 (margin +5.3700) in 512s
```

## Cost, stated before it is spent

`preflight` appends a note that `format_preflight_report` prints — and
`--dry-run` stops right after it:

```
notes:
  - unified segment: world size 4, taken from the member set (tp4, tep4, dep4)
  - members: tp4, tep4, dep4 -> 3 x (boot + accuracy) per unit, 12 accuracy gate(s) over 4 unit(s): core, mtp, multimodal, host_offload
```

When the member sets differ per unit the note switches to the per-unit form
(`core: tp4, tep4, dep4; multimodal: tep4`) and the total is still exact —
10, not 12, for that example.

## The witness gates: first member only

**Decision: `host_offload` and `disagg` run their witness at `members[0]`,
not over the whole set.** The reasoning, which is in the code comment at the
call site:

Boot and accuracy ask *"does this configuration work"*, and the answer
genuinely differs per member — that is the entire finding. A witness asks
something else. It is a **contrast between two legs of the same
configuration**: a device-memory delta with token identity for `host_offload`,
token identity across the prefill/decode hop for `disagg`. What it proves is a
property of the modeling code — the tensor is not resident, the per-sequence
state survives the hop — not a property of the topology.

The residency witness makes that concrete and decisive. Its verdict is a delta
against `accuracy.witness.<unit>.expected_mib`, a **single** number the spec
derives from the checkpoint's own shapes. It is not a per-member number: TEP
shards attention weights and DEP replicates them, so the resident baseline
moves between members while the expectation does not. Looping the witness
would therefore compare each member's delta against a prediction computed for
one of them — a gate that fails or passes for a reason unrelated to the
feature.

Cost seals it: each witness is two full engine launches, so it is the most
expensive gate shape in the set, and the loop would triple it to re-ask a
question whose answer does not vary with the member.

The member is still **passed through** rather than left unset. A witness run
with `member=None` under `unified` resolves to pure tensor parallelism — a
configuration the target may not even be delivered at — so `witness_command`,
`run_residency_witness` and `run_equivalence_witness` all take `member` and
stamp it on the verdict (`[PASS] residency@tep4: ...`).

## What the finding did not anticipate

1. **`preflight` hardcoded the unified world size to 4.** The finding treats
   the world size as settled ("`preflight.py` already defaults that to 4") and
   proposes `members` purely as a gating list. But `parse_parallel_segment`'s
   own docstring says the member set decides the world size, and preflight was
   ignoring that — so `parallel: unified` plus `members: [tp8, tep8, dep8]`
   would have **claimed four devices and gated at eight**, or more likely
   failed the device claim with a number nobody asked for. Caught by the
   first workflow-level test, which declared world-size-1 members and watched
   preflight try to claim 4. Fixed: the world size is read from the first
   member (the schema guarantees they agree), with 4 as the documented
   fallback when no member is declared either.

2. **The witness gates were in the blast radius.** `witness.py` calls
   `topology_flags` through `witness_command`, so making `topology_flags`
   member-aware without touching it would have left both witnesses running at
   TP-only under `unified` — the original defect, surviving in the one place
   the finding does not mention. They now take the member; see the decision
   above for why they take *one*.

3. **Two pre-existing tests asserted formatting, not routing.**
   `test_gate_wiring.py` sliced `_assemble_one_unit`'s source on
   `")\n            )"` — twelve literal spaces — to isolate a gate call.
   Moving the calls one level in to loop over members broke them for a reason
   that has nothing to do with what they check. Rewritten to slice by line
   count; the assertions themselves (`unit=unit` reaches the boot and accuracy
   gates) are unchanged.

4. **`GateResult.summary()` was the only label anything reads.** The
   `progress.yaml` entries, the journal, the reviewer prompt, `_close_run` and
   the auditor prompt all funnel through it, so putting the member there
   (`name@member`) covered every consumer with one change — but it also means
   `GateLog.last("boot")` still matches on `name`, deliberately untouched, so
   the delivery phase's "did a boot gate pass" question keeps working
   unchanged across members.
