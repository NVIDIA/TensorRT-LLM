## The socket-length limit, measured

Bound an `AF_UNIX` socket against synthetic paths of each length, no GPU
needed:

| path length | result |
|---|---|
| 100–107 | binds |
| 108–114 | `OSError: AF_UNIX path too long` |

So the kernel cap is **107 inclusive**, matching ZeroMQ's own
`is longer than 107 characters`. And
`len("rpc_test_") + len(str(uuid.uuid4()))` is `9 + 36 == 45`.

`get_unique_ipc_addr` in `tensorrt_llm/executor/rpc/rpc_common.py` builds the
path with `os.path.join(tempfile.gettempdir(), file_name)`, which inserts a
separator. So:

```
MAX_TMPDIR_LEN = 107 - 45 - len("/") = 61
```

This is asserted in the suite against a live bind at exactly 61 and exactly
62, so the derivation is checked against the kernel rather than against
itself.

## What the findings did not anticipate

**1. The bound is 61, not 62.** F006 computed `107 - 45` and got 62. The
separator `os.path.join` inserts is the third term, and dropping it admits
exactly one `TMPDIR` — a 62-character one — that does not work. The
implementation uses the measured 61 and the message says 61; the constant is
derived as `UNIX_SOCKET_PATH_MAX - RPC_SOCKET_BASENAME_LEN - len("/")` so the
subtraction is visible rather than folded into a literal.

**2. `task.yaml` still declared the 92-character `TMPDIR`.** The brief said it
already carried the 49-character Lustre spelling; it did not — both `TMPDIR`
and `CLAUDE_CODE_TMPDIR` were still
`/scratch/.../users/<user>/staircase-tmp`, which the new check correctly
rejects. Moved to `/lustre/<fs>/portfolios/<org>/users/<user>/tmp4` (49
characters, `rpc_test_<uuid4>` under it is 95 and binds) with a comment giving
the arithmetic, so the next author does not shorten it back by accident.

**3. `RunEnvironment.command` was not the only place emitting the broken
line.** `_describe_spool` — the prompt block every agent reads under
`session_spool` — independently emitted
`mpirun -n N --allow-run-as-root trtllm-llmapi-launch <your command>`. Fixing
only `command` would have left every agent hand-reproducing both defects, and
the F007 half presents as an engine that never boots. Both now render through
the same `_mpirun_launch`, and a test asserts the prompt quotes the line the
orchestrator will run. The prompt also now says **"Copy that line whole"** with
one sentence on what each flag is for, because an agent that tidies away an
`env -u SLURM_...` prefix it does not recognise gets a silent hang.

**4. The length bound is on `TMPDIR` only.** `check_tmpdir` loops over
`TMPDIR` and `CLAUDE_CODE_TMPDIR`, but only the former hosts the RPC socket.
Holding the harness's scratch dir to a socket's budget would reject a value
that works, for a reason that is not true of it. Tested both ways.

**5. `--oversubscribe` and the scrub share a home, not just a branch.** They
are both properties of *"running `mpirun` inside someone else's allocation"* —
which is the one thing the non-Slurm branch does and the `slurm` branch never
does. They live together in `_mpirun_launch`, whose docstring states the
asymmetry once for both rather than twice.

**6. Worth reporting upstream (restating F007).** `trtllm-llmapi-launch`
preferring `SLURM_PROCID` unconditionally produces the worst available failure
mode when the assumption breaks: not an error and not a wrong answer, but N
silent single-rank runs that hang forever. A cheap guard would be to compare
the two when both are present and refuse to start on disagreement —
`SLURM_PROCID=0` alongside `OMPI_COMM_WORLD_RANK=3` is not a situation any
correct launch produces, and neither is `SLURM_NTASKS=1` alongside
`OMPI_COMM_WORLD_SIZE=4`. Not filed as part of this change.
